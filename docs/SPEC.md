## Роль и цель

Ты — senior Flutter/Dart разработчик с опытом Supabase и PostgreSQL. Твоя задача — спроектировать и реализовать веб-платформу для тренировки заданий ЕГЭ-2027 по информатике, где нужно писать код на Python. Платформа по духу похожа на Codewars: каталог задач, редактор кода, запуск Python прямо в браузере, отправка ответа, проверка на сервере, прогресс, просмотр чужих решений после своего верного.

Пользователи: небольшая группа (ученица, несколько друзей, администратор). Бюджет — ноль: только бесплатные тарифы.

Качество кода — главный приоритет. Проект не должен превратиться в свалку: чистая архитектура, ООП, SOLID, DRY, KISS, строгая типизация, тесты, линтеры. Лучше меньше функций, но сделанных правильно.

## Архитектура фронтенда

**Clean Architecture + feature-first.** Слои внутри каждой фичи:

```
lib/
  main.dart
  app/                     # App, роутер, тема, DI-провайдеры верхнего уровня
    router/
    theme/
  core/                    # общее, без бизнес-логики фич
    error/                 # Failure, Result
    network/               # обёртка над Supabase-клиентом
    python_runtime/        # абстракция PythonRuntime + реализация на Pyodide
    widgets/               # переиспользуемые UI-компоненты
    utils/
    config/                # Env (через --dart-define)
  features/
    auth/
      domain/              # entities, repository interfaces, use cases
      data/                # DTO, datasources, repository implementations
      presentation/        # screens, widgets, controllers (Riverpod)
    tasks/                 # каталог и страница задачи
    editor/                # редактор, запуск, консоль
    submissions/           # отправка, история попыток, чужие решения
    profile/               # прогресс, статистика
    admin/                 # панель администратора
web/
  pyodide_worker.js        # Web Worker для Pyodide
  index.html
test/                      # зеркалирует lib/
supabase/
  migrations/              # SQL-миграции (схема, RLS, функции)
  seed/                    # скрипт загрузки задач
tasks/                     # банк задач (условия + файлы), БЕЗ ответов
.github/workflows/
```

Правила:
- **Domain** не зависит ни от Flutter, ни от Supabase. Только чистый Dart.
- **Presentation** общается только с use case'ами или интерфейсами репозиториев, но не с Supabase напрямую.
- **Dependency Inversion:** интерфейсы в domain, реализации в data, связывание через Riverpod-провайдеры.
- **Single Responsibility:** виджет не длиннее ~150 строк. Большие экраны разбиваются на компоненты.
- Выполнение Python скрыто за интерфейсом `PythonRuntime` (`run(code, stdin, files, timeout) → RunResult`), чтобы реализацию можно было заменить (например, на серверный Judge0) без изменения UI.
- Никаких магических строк: маршруты, ключи, имена таблиц и RPC держать в константах.
- Все ошибки — типизированные `Failure`, в UI показываются понятные сообщения на русском.
- Интерфейс только на русском, строки собраны в одном месте (ARB/l10n), чтобы их легко было править.

## Выполнение Python (Pyodide)

- Pyodide загружается лениво (при первом открытии редактора) с CDN jsDelivr. Пока идёт загрузка, показывается индикатор.
- Выполнение идёт **в Web Worker**, чтобы UI не зависал.
- **Таймаут** настраивается, по умолчанию 60 с. Кнопка «Стоп» вызывает `worker.terminate()` и пересоздаёт воркер. Учитывай, что Pyodide в 1,5–3 раза медленнее CPython.
- Перед запуском файлы задания скачиваются с GitHub Pages и записываются в виртуальную ФС Pyodide под **оригинальными именами**, чтобы `open('24.txt')` работал как на экзамене.
- Поддерживаются `stdin` (поле ввода, подменяем `sys.stdin`) и `input()`.
- `stdout` и `stderr` захватываются и показываются в консоли. Трассировка ошибок отображается читаемо.
- Доступны стандартная библиотека (`itertools`, `functools`, `math`, `collections`, `sys.setrecursionlimit`) и `turtle` (либо заглушка для задания 6).
- Файлы кешируются в памяти сессии, повторно не скачиваются.

## Авторизация (без email)

Письма не отправляем, почта не нужна.

- Вход и регистрация по **логину и паролю**. Под капотом логин превращается в техническую почту `<username>@ege.local`. В Supabase отключено подтверждение email.
- Логин: латиница, цифры, `_`, от 3 до 20 символов, уникальный. Пароль: минимум 8 символов.
- Есть переключатель «Регистрация открыта/закрыта» (флаг в таблице `app_settings`). Администратор может закрыть регистрацию, чтобы на сайт не заходили посторонние.
- Сессия хранится стандартно через `supabase_flutter`.
- Роли: `student` (по умолчанию) и `admin`. Роль хранится в `profiles.role`. Выдать роль admin можно только SQL-запросом или из админки другим админом.
- Сброс пароля: администратор задаёт новый пароль через RPC-функцию с проверкой роли.

## База данных (Supabase Postgres)

Всё оформляется **SQL-миграциями** в `supabase/migrations/`. Изменения через UI дашборда не допускаются.

Таблицы (минимум):

- `profiles`: `id uuid PK → auth.users`, `username text unique`, `role text check in ('student','admin')`, `created_at`.
- `tasks`: `id`, `slug unique`, `ege_number smallint`, `title`, `statement_md`, `difficulty smallint (1–3)`, `answer_format text` (`single` | `pair` | `multi` | `string`), `files jsonb` (список путей на GitHub Pages), `tags text[]`, `is_published bool`, `source text` (откуда задача), `created_at`.
- `task_answers`: `task_id PK → tasks`, `answer text`. **Клиенты не могут читать эту таблицу ни при каких условиях.**
- `submissions` (попытка — одна отправка ответа): `id`, `user_id`, `task_id`, `code text`, `answer text`, `is_correct bool`, `is_published bool default false`, `published_at timestamptz null`, `created_at`. Constraint: `is_published` может быть `true` только при `is_correct = true`.
- `app_settings`: ключ–значение (`registration_open`, и т.п.).

Представление или RPC `user_progress`: для каждого пользователя и `ege_number` — сколько задач решено из скольких.

**RLS включён на всех таблицах.** Политики:
- `tasks`: чтение для authenticated, где `is_published`; админ читает и пишет всё.
- `task_answers`: никакого доступа через API (без политик для anon и authenticated).
- `submissions`:
  - пользователь читает свои попытки;
  - пользователь читает **опубликованные** (`is_published = true`) попытки других по задаче, только если у него самого есть верная попытка по этой задаче;
  - админ читает всё, включая неопубликованные и неверные попытки;
  - **INSERT и UPDATE напрямую запрещены**, только через RPC.
- `profiles`: чтение `username` для authenticated; изменять свою роль нельзя.

RPC-функции (`security definer`, `set search_path = public`, с проверкой `auth.uid()`):
- `submit_solution(p_task_id, p_code, p_answer) → jsonb {is_correct, submission_id}`. Нормализует ответ (обрезает пробелы, схлопывает пробельные символы, для числовых форматов сравнивает поэлементно), сравнивает с `task_answers`, пишет в `submissions`. Ограничение частоты: не больше N отправок в минуту на пользователя.
- `admin_reset_password(p_user_id, p_new_password)` — только для админа.
- `set_solution_published(p_submission_id, p_published bool)` — автор публикует или снимает с публикации **свою верную** попытку. Для неверной попытки или чужой — ошибка. Выставляет `published_at`.
- `admin_set_role(...)`, `get_user_progress(p_user_id)`.

Добавь pgTAP-тесты или хотя бы SQL-скрипт, который проверяет RLS: студент не видит ответы, не видит чужие решения до решения своего, не может вставить попытку напрямую.

## Банк задач и загрузка (seed)

- Каждая задача лежит в своей папке: `tasks/<ege_number>/<slug>/`:
  - `task.yaml` — метаданные (`title`, `ege_number`, `difficulty`, `answer_format`, `tags`, `source`);
  - `statement.md` — условие;
  - файлы данных (`24.txt`, `27_A.txt`, `27_B.txt`).
- **Ответы не хранятся в публичном репозитории.** Они лежат в `seed/answers.local.json` (в `.gitignore`) или в секрете GitHub Actions.
- Скрипт `supabase/seed/seed_tasks` (на Dart или Python) идемпотентно выполняет upsert задач и ответов через service role key. Ключ берётся только из переменной окружения и никогда не попадает во фронтенд.
- Файлы данных при сборке копируются в `build/web/task_files/...`.
- Для старта подготовь по 1–2 задачи-примера для каждого основного номера (16, 17, 23, 24, 25, 26, 27) и по одной на несколько дополнительных. Используй **собственные формулировки** (стилизованные под ЕГЭ), а не копии чужих материалов.

## Экраны и функции

1. **Вход / Регистрация.** Логин и пароль, валидация, понятные ошибки.
2. **Каталог задач** (главная):
   - сетка или список карточек, сгруппированных по номеру ЕГЭ (чипы-фильтры 2…27);
   - фильтры: номер, сложность, статус (решено / не решено / пробовал), поиск по названию;
   - на карточке: номер ЕГЭ, название, сложность (цветная метка, как «kyu» на Codewars), статус, процент решивших.
3. **Страница задачи:**
   - на десктопе: слева условие (markdown) и ссылки для скачивания файлов, справа редактор, консоль и поле ответа;
   - на мобильном: вкладки «Условие / Код / Результат»;
   - кнопки «Запустить», «Стоп», «Отправить ответ»; поле stdin (сворачиваемое);
   - код-черновик автоматически сохраняется локально для каждой задачи;
   - после отправки: крупная понятная индикация «Верно / Неверно», история моих попыток;
   - **публикация решения (как на Codewars):** после верного ответа появляется блок «Задача решена!» с кнопками «Опубликовать решение» и «Не сейчас». Публиковать можно только верную попытку. В истории своих попыток у каждой верной есть переключатель «Опубликовано», его можно снять позже. Код опубликованного решения не редактируется: чтобы улучшить решение, нужно отправить новую попытку и опубликовать её;
   - вкладка «Решения» открывается после своего верного ответа и показывает **только опубликованные** решения других учеников (логин, дата, код с подсветкой), сначала новые. Если опубликованных решений нет, показывается пустое состояние.
   - Решения хранятся только в Supabase. Ученики с git не взаимодействуют.
4. **Профиль:** прогресс по каждому номеру ЕГЭ (прогресс-бары), всего решено, серия дней, последние попытки.
5. **Админка** (только роль admin, подробно в разделе «Ролевая модель»).
6. **404** и страница ошибки.

## Ролевая модель (ключевое требование)

Две роли: **admin** (преподаватель) и **student** (ученик). Роль определяет навигацию, доступные экраны и права в БД (RLS). Проверка роли выполняется **и на клиенте** (guard'ы go_router, скрытие пунктов меню), **и в базе** (RLS и RPC). Клиентская проверка нужна только для удобства, защиту обеспечивает база.

**Ученик:**
- видит каталог опубликованных задач и решает их;
- видит только **свои** попытки и свой прогресс;
- видит чужие **опубликованные** решения задачи только после своего верного ответа;
- решает, публиковать ли своё верное решение; неверное опубликовать нельзя;
- не видит список других учеников и чужой прогресс.

**Админ:**
- **Список учеников:** таблица с логином, датой регистрации, датой последней активности, числом решённых задач, числом попыток и процентом верных. Поиск по логину и сортировка по любой колонке.
- **Карточка ученика:**
  - прогресс по каждому номеру ЕГЭ (решено / всего);
  - список задач со статусом для этого ученика: решено, пробовал без успеха, не начинал; число попыток и дата последней;
  - по клику на задачу — **все попытки ученика по ней в хронологическом порядке**, включая неверные и неопубликованные: код с подсветкой, отправленный ответ, верно или неверно, опубликовано или нет, время. Можно переключаться между попытками и видеть, как решение менялось.
- **Лента последних попыток всех учеников:** фильтры по ученику, номеру ЕГЭ, задаче, результату и периоду. Ведёт в ту же карточку попытки. Это основной способ для админа видеть, что ученики присылают.
- **Страница задачи для админа:** помимо условия, список учеников, которые её решали, и их результаты. Эталонный ответ показывается только админу.
- **Управление:** опубликовать или скрыть задачу, открыть или закрыть регистрацию, сбросить пароль ученику, назначить или снять роль admin.
- Админ тоже может решать задачи, но его попытки не попадают в статистику учеников.

**Вне рамок MVP (не реализовывать):** комментарии к решениям, лайки, личные сообщения, уведомления, чаты. Админ общается с учениками вне платформы.

Для админских списков нужны RPC-функции или представления с проверкой роли (`admin_list_students()`, `admin_student_overview(p_user_id)`, `admin_task_attempts(p_user_id, p_task_id)`, `admin_recent_submissions(filters, limit, offset)`) с пагинацией. Не выгружай все попытки на клиент.

## Дизайн

- **Тёмная тема по умолчанию** (светлую можно добавить позже, но архитектура `ThemeData` должна это позволять).
- Вдохновение — Codewars: тёмный графитовый фон, один акцентный цвет (например, насыщенный красный или оранжевый), цветные метки сложности, моноширинный шрифт для кода. Копировать их логотипы, иконки и фирменные элементы нельзя, стиль должен быть собственным.
- Просто и со вкусом: много воздуха, чёткая типографика (например, Inter / JetBrains Mono через `google_fonts` или локальные ассеты), никаких лишних градиентов и теней.
- Дизайн-токены (цвета, отступы, радиусы, типографика) в одном месте (`app/theme`), без хардкода в виджетах.
- **Адаптивность:** брейкпоинты mobile < 600, tablet < 1024, desktop. Используй `LayoutBuilder`. На мобильных — нижняя навигация, на десктопе — боковая или верхняя.
- Доступность: достаточная контрастность, размер тап-целей не меньше 44 px, фокус с клавиатуры, горячая клавиша Ctrl/Cmd+Enter для запуска.
- Оптимизация веба: рендерер по умолчанию (CanvasKit/skwasm), индикатор загрузки в `index.html`, чтобы первый экран не был пустым.

## Качество, тесты, CI

- `very_good_analysis`: 0 предупреждений. `dart format` обязателен.
- Юнит-тесты для use case'ов, репозиториев (на моках), нормализации ответов и контроллеров. Виджет-тесты для ключевых экранов. Цель — покрытие domain/data не ниже 80%.
- Никаких `print`, только логгер. Никаких `dynamic` без необходимости.
- Секреты: `SUPABASE_URL` и `SUPABASE_ANON_KEY` передаются через `--dart-define` (anon key публичный, это нормально; безопасность обеспечивает RLS). Service role key не попадает во фронтенд никогда.
- `README.md`: архитектура, локальный запуск, как добавить задачу, как задеплоить, как выдать админа.

GitHub Actions:
1. `ci.yml` — анализ, тесты и сборка на каждый PR.
2. `deploy.yml` — `flutter build web --release --base-href /<repo>/`, копирование файлов задач, деплой на GitHub Pages. Для глубоких ссылок добавь SPA-фоллбек через `404.html`.
3. `keepalive.yml` — каждые 3 дня лёгкий запрос к Supabase, чтобы бесплатный проект не уснул.
4. `backup.yml` — еженедельный `pg_dump` в артефакт или приватный репозиторий (строка подключения берётся из секрета).
5. `seed.yml` — ручной запуск загрузки задач.

## Критерии готовности MVP

- Новый пользователь регистрируется по логину без почты и видит каталог.
- В задаче 24 код `open('24.txt')` читает файл, выводит результат, ответ отправляется и засчитывается.
- Ответ задачи нельзя узнать ни из фронтенда, ни через API с anon key.
- Чужие решения недоступны до своего верного ответа (проверено тестом RLS).
- Бесконечный цикл останавливается кнопкой «Стоп» или по таймауту, интерфейс не зависает.
- Сайт нормально работает на телефоне (ширина 360 px) и на десктопе.
- Админ видит список учеников, открывает любого и просматривает всю историю его попыток с кодом по каждой задаче.
- Ученик не может получить список учеников или чужие попытки через API (проверено тестом RLS).
- CI зелёный, анализатор без предупреждений.
