# Задание: залить ответы банка ФИПИ в боевую базу и опубликовать 139 задач

## Зачем

Покрывающий набор банка решён: 199 ответов подтверждены `solve.php`, к
каждому есть эталон, а приёмка перепроверила их независимо
(`docs/SOLVE_REPORT.md`, раздел 10). Но ответы лежат только в выгрузке,
а в базе все задания банка — черновики без ответа. Ученик видит одну задачу.

Задача — записать в базу ответы, форматы и эталоны 199 задач, сверить
эталоны штатной функцией и опубликовать 139 задач, которые клиент уже
умеет показывать.

Прочитать перед работой:

- `docs/SOLVE_REPORT.md`: разделы 3 (формат ответов), 5, 7 и 10;
- `docs/content-api.md`, `tools/content_client.py`, `tools/import_repo_tasks.py`;
- `supabase/migrations/20260921100002_fipi_functions.sql` (`admin_upsert_task`),
  `20260917130002_content_functions.sql` (`assert_content_admin`,
  `admin_verify_reference`, `admin_set_task_status`);
- `supabase/tests/rls_tests.sql`, раздел (п), и `supabase/tests/import_checks.sql`.

## Часть 1. Локально

### 1.1. RPC `admin_set_task_answer`

Новая миграция в `supabase/migrations/`, метка позже `20261006100000`, имя
по смыслу. Заголовок-комментарий на русском, стиль — как у соседних функций.

Контракт:

```
admin_set_task_answer(payload jsonb) → jsonb
payload: slug, answer, answer_format, reference_solution, answer_explanation (необязательно)
ответ:   { "slug": …, "status": …, "answer_format": … }
```

- Проверки — те же, что у `admin_upsert_task` для этих полей: формат из
  `single`/`pair`/`multi`/`string`, ответ непустой и проходит
  `normalize_answer`, строковый — в одну строку, эталон непустой. Коды
  ошибок — существующие: `bad_payload`, `not_found`, `bad_answer_format`,
  `bad_answer`, `missing_reference_solution`. Новых кодов не вводить.
- Меняет **только** `tasks.answer_format`, `reference_solution`,
  `answer_explanation`, ответ в `task_answers` и сбрасывает
  `reference_verified_at`. Опубликованная задача уходит в `review`,
  черновик остаётся черновиком. Файлы, темы, связи со справочником,
  условие, номер и прочее не трогает.
- Начинается с `assert_content_admin()`, пишет `write_audit(…, 'set_answer', 'task', slug, …)`.
- `security definer`, `set search_path = public, extensions`; `revoke … from
  public, anon`, `grant execute … to authenticated`.
- Работает для задачи любого `origin`, не только банка.

Тесты — новый раздел `rls_tests.sql`:

- ученик получает `[forbidden]`, аноним — permission denied;
- администратор задаёт ответ задаче, у которой есть файл с адресом в
  Storage и две темы. После вызова файлы (число, имена, `storage_path`) и
  темы те же, ответ записан, формат сменился, отметка сверки сброшена;
- опубликованная задача после вызова — `review`, черновик — `draft`;
- каждая ошибка из списка выше;
- после вызова ученик по-прежнему не видит ответ.

Раздел (п) — полная матрица прав. Новую функцию дописать в ожидаемое,
иначе тест упадёт. Так и задумано.

### 1.3. Скрипт `tools/import_fipi_answers.py`

Python 3.9, только стандартная библиотека. Content API — через
`ContentClient` из `tools/content_client.py`, туда же добавить метод
`set_answer`. Свой HTTP-клиент не писать.

- Берёт записи `solutions.json` с `verified: true` (199). Каталог выгрузки —
  аргумент `--dump`, по умолчанию `~/projects/ege-informatics-2027`.
- Для каждой задачи:
  1. `set_answer`;
  2. запуск эталона локально (`python3`, рабочий каталог `assets/files/`,
     таймаут 60 с);
  3. `verify_reference(slug, вывод)`, ответ должен быть `matches: true`.
     Несовпадение — ошибка задачи и стоп, а не пропуск.
- **Повторный запуск безопасен.** Задача, у которой ответ, формат и эталон
  уже совпадают с `solutions.json`, а эталон сверен, пропускается (сверить
  через `get_task`). Иначе повтор снял бы публикацию.
- `--publish` публикует задачи, отобранные правилом: подтверждена, в
  `tasks.json` выгрузки нет `assets`, нет `parent_id`, нет
  `condition_incomplete` и `duplicate_of`. Перед публикацией каждой
  `get_task` должен показать пустой список файлов. Если по правилу
  отобрано не 139 задач, ничего не публиковать и остановиться.
- `--slug` — одна задача. `--dry-run` — без сети: запускает все эталоны,
  сравнивает вывод с ответом по правилам `normalize_answer` и печатает
  «к заливке: 199, к публикации: 139».
- **Темп**: не больше 50 вызовов `admin_*` в минуту. На `[rate_limit]` —
  пауза 60 с и повтор. Настройку `content_writes_per_minute` не трогать.
- **Ответы и эталоны не печатать** ни в вывод, ни в журнал: вывод попадает
  в транскрипт сессии. Печатать `slug`, этап и итог.

Юнит-тесты — `tools/tests/test_import_fipi_answers.py` (unittest, клиент
подменяется заглушкой): отбор 199 и 139 на маленькой искусственной выгрузке,
пропуск уже залитой задачи, стоп на `matches: false`, повтор после
`[rate_limit]`, отказ публиковать при числе ≠ 139, в выводе нет ответа.
