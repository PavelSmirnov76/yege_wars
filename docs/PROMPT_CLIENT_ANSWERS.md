# Задание: ответ по формату и справка по темам на странице задачи

## Зачем

На боевой опубликованы 139 задач банка ФИПИ и одна задача проекта. Отвечать
на них в клиенте неудобно, а местами почти невозможно:

- **Табличные ответы** (`multi`, 8 опубликованных задач номера 25, в таблице
  до 9 строк) надо вводить вручную: числа через пробел, по строкам. Кнопка
  «Взять из вывода» подставляет только последнюю строку, а подсказки
  о форме ответа нет вовсе.
- **Подсказка под полем ответа** одна на все задачи: «То, что нужно
  записать в бланк». Платформа сравнивает строгую форму: номер варианта,
  запятая без пробела, регистр букв.
- **Справки нет ни у одной опубликованной задачи.** Клиент читает её из
  `task_references`, а там на боевой 0 строк. После импорта банка справка
  идёт по темам, через представление `task_articles`.

Задача — исправить эти три вещи в клиенте. Схема БД и боевая база
не меняются.

Прочитать перед работой: `CLAUDE.md`, `docs/STATE.md` (контракты кода,
раздел «Чего ещё нет»), `docs/IMPORT_ANSWERS_REPORT.md` (разделы 5 и 6).

## Что сделать

### 1. Формат ответа — перечисление в domain

`AnswerFormat` (`single`, `pair`, `multi`, `string`) с разбором значения из
базы; неизвестное значение не роняет экран. `TaskDetail.answerFormat` —
этого типа. Строковые значения — только в одном месте.

### 2. «Взять из вывода» по формату

- `multi`: все непустые строки вывода (каждая без пробельных краёв) через
  один пробел, порядок сохраняется. Так таблица «по строкам» превращается
  в то, что ждёт платформа.
- Остальные форматы — последняя непустая строка, как сейчас.

Правило — чистая функция или метод в domain-слое `submissions`, а не
в виджете. Юнит-тесты на каждый формат, на пустой вывод и на вывод
с пустыми строками.

### 3. Подсказка о форме ответа

Под полем ответа — подсказка по формату, вместо общей. Строки — в
`lib/l10n/app_ru.arb`. Черновик формулировок (смысл сохранить, слова
можно уточнить):

| Формат | Подсказка |
|---|---|
| `single` | Одно число. Если в условии даны варианты — номер варианта |
| `pair` | Два числа через пробел |
| `multi` | Числа через пробел. Таблицу — по строкам, слева направо |
| `string` | Точно как требует условие: регистр, запятые и пробелы важны |

### 4. Ответ без пробельных краёв

`SubmitAnswerUseCase` срезает с краёв все пробельные символы, включая
переводы строк, и отправляет уже обрезанный ответ. `normalize_answer`
в базе не трогать: это отдельное решение.

### 5. Справка по темам

Справка задачи — это статьи по её темам плюс ручные связи:

- статьи по темам: `task_articles` по `task_id`, затем `reference_articles`
  по списку `article_id` (`in.(…)`), колонки — как сейчас у ручных связей.
  Два запроса, без изменения схемы;
- ручные связи из `task_references` — как сейчас;
- `relevance`: статья основной темы (`sort_order = 0`) — `primary`, других
  тем — `related`, ручная связь — со своим значением;
- одна статья — один раз (по `slug`). Если статья пришла и по теме, и
  вручную, берётся более сильная `relevance`;
- порядок: главные первыми, внутри — по `sort_order` темы, затем ручные.

Имена представления и колонок — в константах `lib/core/network/supabase_schema.dart`.
Слияние и порядок — в репозитории или domain, не в виджете. Юнит-тесты
на слияние, дубли и порядок. Виджет-тест: у задачи без ручных связей,
но с темой, показывается статья по теме.

### 6. Проверка запросов на боевой (только чтение)

Виджет-тесты работают на заглушках, поэтому формы запросов проверяются
на настоящем PostgREST: те же `select`, что делает клиент, GET-запросами
под сервисным аккаунтом (`CONTENT_API_LOGIN`, токен — через
`tools/content_client.py`). Для `fipi-9c9ef1` и `e24-longest-run` справка
должна вернуть статью основной темы. Значения переменных окружения
не выводить. Никаких записей в базу.

### 7. Документация

`docs/STATE.md`: раздел о доработке. В «Чего ещё нет» убрать пункт про
справку из `task_references`, а пункт про подсказку о форме ответа
сократить до того, что осталось. Остальное не переписывать.
