Банк ФИПИ импортирован и 2026-09-22 залит в боевую базу, но работа не
закрыта: ветка `fipi-import` не слита в `main`, после заливки остались два
хвоста на боевой и одна неверная проверка. Задача — довести всё это до

- `tools/import_repo_tasks.py`, `tasks/*/*/task.yaml`.

## Часть 1. Локально

### 1.1. Шим повторяет права по умолчанию Supabase

Сейчас `supabase/tests/shim_local.sql` не выдаёт ролям права по умолчанию,
которые Supabase выдаёт на новые объекты в `public`. Поэтому лишние права
вроде тех, что у `task_articles`, локально не видны, и тест на них проходит
вхолостую.

1. Прочитать с боевой (только чтение):
   ```sql
   select current_user;
   select pg_get_userbyid(defaclrole) as owner,
          defaclnamespace::regnamespace as schema,
          defaclobjtype, defaclacl
     from pg_default_acl order by 1, 2, 3;
   ```
2. Воспроизвести в шиме ровно то, что относится к роли, под которой
   применяются миграции, и к схеме `public`. Ничего не добавлять «для
   полноты» — только то, что показал запрос.
3. Прогнать `bash supabase/tests/run_local.sh` и
   `bash supabase/tests/run_import_check.sh`.

**Стоп-условие.** Если после правки шима упал хоть один существующий тест
или нашлись другие объекты с лишними правами — остановиться и доложить:
какие объекты, какие права, у каких ролей. Самому не чинить, ждать решения.

### 1.2. Миграция: права на `task_articles`

Новый файл в `supabase/migrations/`. Метка времени — позже
`20260921100002`, имя по смыслу. Применённые миграции не редактировать.

- У `anon` и `authenticated` на `public.task_articles` не остаётся ничего,
  кроме `select` у `authenticated`. Стиль — как у `task_themes` в
  `20260921100001_fipi_rls.sql`, заголовок-комментарий на русском.
- Тест в `supabase/tests/rls_tests.sql`: `authenticated` не может писать в
  `task_articles`, `anon` не имеет к нему доступа.
- **Доказать, что тест не холостой**: прогнать `run_local.sh` без новой
  миграции (временно убрав файл) и показать, что тест падает. В отчёт —
  вывод обоих прогонов.

Темы задаются через Content API (`admin_upsert_task` принимает массив
`themes`), но `tools/import_repo_tasks.py` их не передаёт. Перезаливка любой
задачи проекта оставила бы её с темой `none`.

1. В `task.yaml` каждой из 10 задач добавить `themes` — код КЭС номера по
   плану КИМ-2026 (`~/projects/ege-informatics-2027/docs/kim_plan_2026.json`,
   поле `кэс`):

   | 16 | `e16-rec-branch` | 3.7 |
   | 17 | `e17-pairs-file` | 3.10 |

2. `import_repo_tasks.py` передаёт `themes` в payload. Если в `task.yaml`
   тем нет или список пуст, это ошибка подготовки задачи, а не молчаливое

3. Юнит-тест в `tools/tests/` (unittest, Python 3.9 — без `match`): темы
   попадают в payload, а без тем подготовка падает с понятной ошибкой.

### 1.4. `import_checks.sql` считает только банк

Файл написан под пустую базу. На боевой из-за ручной задачи шесть пунктов
дают +1 (5, 14, 19, 20, 21, 23). Когда у неё появится тема 3.9, разойдутся
ещё пункты 3 и 4.

Принцип такой. Пункты, которые сверяют число с выгрузкой, считают только
`origin = 'fipi'`. Инварианты («нарушений 0») считают всю базу там, где
правило действует для любой задачи. Пройти все 26 пунктов, а не только
названные выше.

- Ожидаемые числа **не менять** — меняется только то, что считается.
- Ловушка: у задач проекта файлы лежат в `task_files.content`, без адреса в
  Storage. Поэтому п. 21 — про банк, а не инвариант всей базы.
- Обновить комментарий в шапке файла: теперь проверка верна на любой базе,
  а не только на пустой.
- `bash supabase/tests/run_import_check.sh` → `IMPORT OK`.
