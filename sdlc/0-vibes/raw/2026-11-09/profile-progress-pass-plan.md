## Первое задание

Ученик решает задачу, открывает профиль и видит обновлённую сводку.
Он может открыть задачу из списка последних попыток и продолжить работу.
В сдачу входят получение данных, экран, обновление состояния и проверки.

Предлагаемые правила для первого задания

1. Сводка считает текущие опубликованные задачи. «Решено» означает число
   уникальных задач с хотя бы одной своей верной попыткой. Повторное решение
   той же задачи счётчик не увеличивает. Скрытая задача исключается из обоих
   чисел, после повторной публикации прежнее решение учитывается снова.
2. Общая сводка и строки по номерам используют один набор задач. Показываются
   номера с доступными задачами. Для задач без номера есть отдельная строка
   «Без номера КЕГЭ». У нового ученика в числителях нули.
3. В профиле показаны последние 10 своих попыток по текущим опубликованным
   задачам, включая неверные. Поля включают название задачи, номер КЕГЭ,
   вердикт и дату/время. Порядок определяется временем от новых к старым,
   при равном времени — id. Выбор строки открывает эту задачу.
4. При открытии профиля данные запрашиваются заново. После отправки ответа
   и возврата в профиль видны актуальные значения. Данные привязаны к id
   текущего пользователя, при смене аккаунта загружается его сводка.
5. Загрузка, отсутствие попыток, отсутствие опубликованных задач и ошибка
   имеют свои состояния. При ошибке доступен «Повторить». Успешные данные
   и ошибка различаются визуально, ошибка запроса не превращается в нули.
6. У администратора в этом профиле своя статистика. Просмотр учеников
   реализуется на этапе админки. Логин, роль и выход остаются на экране.

Серия дней следует отдельным заданием этапа профиля. Перед ним владелец
выбирает событие занятия и часовой пояс подсчёта.

## Проверенные факты

- Экран профиля содержит логин, роль, заглушку и выход.
  [profile_screen.dart](../../../../lib/features/profile/presentation/screens/profile_screen.dart)
- Последнее определение `get_user_progress(uuid)` считает только
  `status = 'published'`, группирует по `ege_number`, использует `exists`
  верной попытки и допускает чужой прогресс только администратору.
  [content_functions.sql](../../../../supabase/migrations/20260917130002_content_functions.sql)
- RLS позволяет читать свои попытки, а также некоторые чужие. Поэтому
  запрос последних попыток должен явно фильтровать `user_id` текущего
  пользователя и статус задачи, а сервер должен ограничивать результат.
  [rls.sql](../../../../supabase/migrations/20260917120001_rls.sql)
- Общий запрос попыток каталога загружает пары `task_id/is_correct`.
  Для последних попыток нужен ограниченный запрос с временем и задачей.
  [supabase_tasks_remote_data_source.dart](../../../../lib/features/tasks/data/datasources/supabase_tasks_remote_data_source.dart)
- Навигация использует `StatefulShellRoute.indexedStack`. Требуется
  обновление при возвращении в профиль, включая уже открытую ветку.
  [app_router.dart](../../../../lib/app/router/app_router.dart)
- В рабочем дереве есть только основная копия на `main`. Схема dev/боевой
  базы и продуктовые проверки в рамках подготовки плана не запускались.
  Сохранённый базовый прогон задания TASK-11 содержит 399 Flutter-тестов.
  [summary.md](../../../6-eval/auto/2026-11-03-ec9cdc4/summary.md)

## Разница прохода

1. Снять PRD скриптом с этим входом. Добавить в словарь понятия прогресса,
   сводки и последних попыток. Добавить атомарные требования к общей сводке,
   прогрессу по номерам, последним попыткам и переходу из попытки к задаче.
   Уточнить план работ PRD в соответствии с одобренной очередью.
2. Создать одну бизнес-задачу планирования для готового профиля. Основания
   включают новые требования и этот вход. Серию дней ставить следующим
   заданием по отдельно согласованным правилам.
3. Создать модуль PROGRESS, сущность сводки с контрактом данных и доступа,
   события открытия прогресса и выбора последней попытки, UC просмотра
   прогресса и UC перехода к задаче. Переиспользовать актора вошедшего
   пользователя и существующую сущность попытки.
4. В UC просмотра описать успешную загрузку, пустые данные, отказ загрузки
   и повтор. Параметры чисел, номеров, скрытых задач и смены аккаунта
   проверять в тестах соответствующих путей.
5. Заменить FIG-10 новым экраном профиля, сохранив основание UC-4 и UC-13
   и добавив новые UC. FIG-10 похоронить через скрипт. Добавить компоненты
   сводки/прогресса и списка последних попыток, используя текущие токены.
   В новом FIG задать раскладку 360/1440, состояния и ключи l10n.
6. После записи прохода подготовить одно задание реализации и ручной кейс
   для его приёмки. Id выдаёт `sdlc_tool next`. После одобрения коммита
   задания постановщик готовит worktree и передаёт исполнителю запуск.

UC-4 описывает показ логина и роли, UC-13 — выход. Эти контракты продолжают
действовать. При замене FIG исторические ссылки сохраняются скриптом.
Новые документы ссылаются на живые артефакты.

## Проверка результата

Автотесты подтверждают уникальность счётчика, общий набор опубликованных
задач, пустой прогресс, ограничение/порядок последних попыток, фильтр по себе,
обновление после отправки и смены аккаунта, ошибки и повтор.

Один ручной кейс проверяет профиль на 360/1440, переход к задаче и возврат
с обновлённой статистикой. Сценарии контролируемых состояний используют
подмены API. Интеграционная часть читает собственные данные dev-проекта
через реальные запросы и сверяет их со сводкой. Точные запросы и ожидаемые
данные фиксируются при постановке. Проверки качества и этот кейс выполняет
Luna, постановщик сверяет изменения и доказательства.
