# 6 — Проверка

Проверка сдач (`5-results/`) по путям UC (`2-specs/use-cases/`): сделало ли
построенное то, что должно? Это **контроль качества**.

Требование проходит стадию, когда у каждого пути каждого UC, который ему
служит, на `DASHBOARD.md` живой вердикт `PASS`. Дальше — `7-security-check/`.

## Почему пути UC, а не требования

Путь UC — единственная спека, которую можно исполнить: актор, триггер, сущность
и исход — это тест. Акторы, сущности и события — определения. Требования —
замысел, и выполняются они только через UC, которые их реализуют. Поэтому
проверяют пути, а сводка поднимает результат до требования.

## Состав

```
6-eval/
├── auto/<ГГГГ-ММ-ДД>-<хэш>/   машинные прогоны проверок проекта
├── manual/                   ручные тест-кейсы и их раунды
├── acceptance/               приёмки сдач: «принято» или «возврат»
└── DASHBOARD.md              сводка: выполнено ли R7
```

Прошлые прогоны не перезаписывают: по этой истории видна регрессия.

## Сводка отвечает на «готово ли?»

`DASHBOARD.md` по каждому требованию показывает каждый UC, который ему служит,
каждый путь и его последний вердикт. Это единственное место, где на вопрос
отвечают взглядом. Требование без проверенных путей — **непроверенное**, а не
выполненное, и сводка говорит это прямо.

Сводку собирает скрипт, руками её не правят. Правила — в [AGENTS.md](AGENTS.md).
