# TC-19: Профиль с прогрессом и последними попытками

## Цель и приоритет

Проверить новый профиль целиком, включая переход к задаче и обновление
сохранённой ветки. Приоритет высокий, это приёмка TASK-12.

**Пути:** [UC-41-P-01](../../2-specs/use-cases/UC-41-ACTOR-2-EVT-25-ENT-18-PROGRESS-SHOWN-IN-PROGRESS.md#uc-41-p-01), [UC-41-P-02](../../2-specs/use-cases/UC-41-ACTOR-2-EVT-25-ENT-18-PROGRESS-SHOWN-IN-PROGRESS.md#uc-41-p-02), [UC-41-P-03](../../2-specs/use-cases/UC-41-ACTOR-2-EVT-25-ENT-18-PROGRESS-SHOWN-IN-PROGRESS.md#uc-41-p-03), [UC-41-P-04](../../2-specs/use-cases/UC-41-ACTOR-2-EVT-25-ENT-18-PROGRESS-SHOWN-IN-PROGRESS.md#uc-41-p-04), [UC-41-P-05](../../2-specs/use-cases/UC-41-ACTOR-2-EVT-25-ENT-18-PROGRESS-SHOWN-IN-PROGRESS.md#uc-41-p-05), [UC-42-P-01](../../2-specs/use-cases/UC-42-ACTOR-2-EVT-26-ENT-18-PROBLEM-OPENED-IN-PROGRESS.md#uc-42-p-01).

## Предусловия

Тестировщик Luna запускает локальную сборку worktree TASK-12 и отдельный
Chromium по `docs/BROWSER_CHECKS.md`. Выполняет кейс на 1440×900 и 360×800,
для каждой ширины использует свежий контекст и исходные фикстуры.
В сдаче исполнителя переданы драйвер, команды и версии для этих условий.

Часть A использует синтетический аккаунт и сетевые подмены Supabase.
Запросы авторизации, контента и отправки для вымышленных задач обрабатывает
драйвер. Отправка перехватывается до обращения к настоящему API.
Синтетические задачи имеют slug с префиксом `tc19-`, отдельные UUID и
короткие условия, `answer_format = 'string'`, файлы/справка пусты.
Входящие API-запросы, порядок/предел
и число вызовов доступны тестировщику в безопасном журнале.

Исходные данные аккаунта A

- Опубликованные T1 и T2 имеют номер 24, T3 имеет номер null.
- По T1 есть двенадцать своих попыток с возрастающим временем, как минимум
  одна верная и одна неверная. По T2 и T3 есть по одной своей неверной
  попытке, обе новее попыток T1.
- Есть более новая своя попытка скрытой H и более новая чужая опубликованная
  попытка по T1. Обе исключаются из списка последних попыток A.
- У двух включённых попыток одинаковое время и разные id. Драйвер фиксирует
  их ожидаемый порядок по убыванию id.
- Ожидаемая сводка A — 1 из 3, номер 24 — 1 / 2,
  «Без номера КЕГЭ» — 0 / 1. Последних попыток ровно 10,
  порядок вычислен по исходным данным.
- Аккаунт B имеет тот же набор опубликованных задач и ноль попыток.
  При переключении состояние авторизации соответствует B, запросы A
  могут искусственно задерживаться для проверки позднего ответа.

В журнале зафиксировать точные UUID/времена фикстур и ожидаемые десять id.
Драйвер проверяет параметры запросов, а ожидаемые результаты рассчитывает
по исходному набору попыток.

Часть B работает с настоящим dev-проектом, значения берутся из локального
`supabase/.env.dev.local`. Вход выполняется в доступную тестовую учётную
запись. Пользователь и роль фиксируются в журнале, секреты и токены скрыты.
Тестировщик выполняет только чтение данных dev.

## Часть A. Контролируемые состояния

1. Открыть `/#/profile` аккаунтом A с задержанными ответами обоих запросов.
   Видны логин, роль, выход, навигация и индикатор загрузки. Разрешить ответы.
   Появляются 1 из 3, строки 24 и без номера, десять попыток. Сверить
   каждую строку с ожидаемым id, названием, вердиктом и локальным временем.
   Длинное название переносится. Скрытая и чужая попытки отсутствуют.
2. Выбрать попытку T2. Должен открыться `/#/task/{slug T2}` и условие T2.
   Перед выбором ветка каталога может хранить T1. Проверяется точный адрес
   и условие выбранной задачи. Вернуться пунктом «Профиль», проверить новый
   вызов обоих запросов и исходную сводку.
3. Из профиля открыть T2 и отправить синтетический ответ `tc19-synthetic`.
   Подмена submit возвращает верный результат и добавляет свою верную
   попытку T2 в fixture-состояние. Вернуться пунктом «Профиль». Новый
   запрос даёт 2 из 3, 24 — 2 / 2, новая попытка первая. Повторить отправку
   в T2. Общий счётчик остаётся 2, а новая попытка вновь первая.
4. В режиме ошибок отказать только RPC прогресса, затем отдельной загрузкой
   отказать только запросу попыток. Каждый раз показана ошибка и «Повторить».
   Нули как результат ошибки не появляются. В фоне автоматических повторов
   нет. Вернуть успешный режим и нажать «Повторить». Оба запроса повторяются,
   индикатор сменяется актуальными данными. Проверить счётчики вызовов.
5. Открыть профиль B. Показаны 0 из 3, 0 / 2 и 0 / 1, «Попыток пока нет».
   Отдельным режимом вернуть отсутствие опубликованных задач. Видны 0 из 0,
   «Пока нет опубликованных задач» и пустые попытки.
6. Начать загрузку A и задержать ответ. Переключить аккаунт на B, дождаться
   его нулевых данных, затем разрешить старый ответ A. На экране остаются
   логин B, нулевые данные B и пустые попытки. В запросах B стоит id B.
7. Вернуть исходные фикстуры A. Пройти Tab к строке попытки, проверить
   видимый фокус и открыть задачу клавишей Enter. Измерить область активации
   строки, «Повторить» и «Выйти» по TOKEN-6. Проверить раскладку FIG-23,
   полный текст, видимость навигации и отсутствие горизонтальной прокрутки.

## Часть B. Реальное чтение dev

8. Отключить сетевые подмены, войти в тестовый dev-аккаунт и открыть профиль.
   Сверить URL проекта с dev-конфигурацией по признаку окружения. При
   отсутствии входа или доступа записать BLOCKED с конкретным условием.
9. Для текущего id получить настоящие ответы `get_user_progress` и
   ограниченного запроса попыток ENT-18. На основе ответа вычислить суммы,
   порядок, число и безопасные поля последних попыток. Сверить их с UI
   на обеих ширинах. Зафиксировать признаки реальных запросов и параметры
   фильтрации. Пустая история допустима, нулевая сводка сверяется с ответом.
10. Открыть задачу из реальной попытки, если список непустой, и вернуться
    в профиль. При пустом списке переход уже подтверждён частью A.
    Зафиксировать повтор реальных запросов при возврате. Другой аккаунт
    ученика и админское чтение чужого прогресса дополнительно здесь не нужны.

## Доказательства и вердикт

В журнале записать ветку/коммит, окружение, браузер, ширину, команды,
фикстуры, ожидаемое/наблюдаемое по шагам, параметры и число вызовов.
На каждой ширине сохранить кадры загруженного профиля, выбранной задачи,
обновлённой сводки после отправки, ошибки, восстановления, обоих пустых
состояний и B после позднего ответа A. Кадры содержат синтетические данные.
Реальное dev-чтение подтверждается безопасным журналом сравнений.

Ошибки двух запросов проверяются отдельно, кадр одинакового состояния
можно сохранить один раз на ширину с указанием обеих проверок в журнале.
Исправления после провала требуют повторить затронутые шаги.

Часть A подтверждает UI и параметры клиента. Часть B подтверждает совместимость
с настоящим API. Серверная запись попытки и приватность данных проверяются
автотестами и существующими RLS-тестами, результаты приложены к сдаче.

Итоговая строка журнала имеет точный вид `**Вердикт:** PASS`,
`**Вердикт:** FAIL` либо `**Вердикт:** BLOCKED`. PASS требует обе части
на обеих ширинах, данные dev и подтверждённые запросы.
