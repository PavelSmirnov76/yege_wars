# YEGE Wars — закон конвейера

Что действует на всех стадиях. `AGENTS.md` стадии добавляет свои правила
именования и работы и не повторяет написанного здесь.

Зачем нужна каждая стадия — в [README.md](README.md). Здесь только то, чему
агент обязан подчиняться. Порядок прохода и цикл задания — в `RUNBOOK.md`: он
сам не загружается, его открывают, когда начинают проход или задание.

В тексте пути пишутся от `sdlc/` (`0-vibes/raw/<дата>/`), в ссылках — от
файла, где стоит ссылка.

## Роли

- **Владелец** — пользователь. Одобряет план каждого прохода, каждое задание и
  итог каждой приёмки. Без его «да» ничего не коммитится.
- **Постановщик** — агент. Ведёт проходы: PRD, бизнес-задачи, спеки, дизайн.
  Пишет задания (TASK), приёмки (ACC), ручные тест-кейсы (TC) и прогоняет их;
  где нужен живой человек, прогон делает владелец. Пишет и меняет скрипт
  конвейера.
- **Исполнитель** — отдельная сессия агента. Выполняет одно задание и пишет его
  сдачу (RESULT). Свою работу не принимает.

## Артефакт закрыт для изменения, открыт для расширения

Артефакт — файл с id из таблицы ниже. Он заморожен с момента записи в
репозиторий, то есть с коммита: его содержание, id и ссылки больше не
меняются. До коммита это черновик. Работа, которая правила бы артефакт,
создаёт новый.

В замороженном файле можно менять только шапку устаревания, место файла и пути
в ссылках, когда переехал файл, на который они ведут. Место и пути меняет
только скрипт конвейера. Больше ничего и никогда.

Поэтому проход можно безопасно повторять: над неизменным деревом закон ничего
не сдвигает.

## Id вечные

Id — тип и номер: `ACTOR-1`, `R7`, `RESULT-TASK-3-01`. Имя файла — id и
название: `ACTOR-1-STUDENT-IN-AUTH.md`. Id выдаётся один раз, не
переиспользуется и не перенумеровывается. Следующий — на единицу больше
наибольшего когда-либо выданного, считая устаревшие.

| Id | Артефакт | Стадия |
|---|---|---|
| `R{n}` | требование | `0-vibes/prd/` |
| `BT-{n}` | бизнес-задача | `1-business-tasks/` |
| `MOD-{n}` · `ACTOR-{n}` · `ENT-{n}` · `EVT-{n}` · `UC-{n}` | спеки | `2-specs/` |
| `UC-{n}-P-{nn}` · `UC-{n}-O-{nn}` | путь и исход внутри UC | файл UC |
| `TOKEN-{n}` · `COMP-{n}` · `FIG-{n}` | группа токенов, компонент, экран | `3-design/` |
| `TASK-{n}` | задание | `4-tasks/` |
| `RESULT-TASK-{n}-{NN}` | сдача задания | `5-results/` |
| `TC-{n}` · `ACC-TASK-{n}-{NN}` | ручной тест-кейс, приёмка сдачи | `6-eval/` |
| `SEC-{n}` | проверка безопасности | `7-security-check/` |
| `REL-{n}` | выпуск | `8-deploy/` |

Каждый тип id принадлежит одному типу артефакта. Не называть артефакт чужим
id: тест-кейс с именем `UC-12-…` даст глобу `**/UC-12-*.md` два файла.

Повторно выданный id молча переводит все ссылки дерева на чужой артефакт, и
ничего не падает. Поэтому исключений у правила нет.

## Ссылка на артефакт — это id, а не путь

Артефакт цитируют по id: `ACTOR-1`. Путь — это место, а место меняется. Id —
сам артефакт, он не меняется.

В Markdown ссылка на артефакт кликабельна, и её видимый текст — id. Из файла в
`2-specs/use-cases/`: `[ACTOR-1](../actors/ACTOR-1-STUDENT-IN-AUTH.md)`;
требование и путь UC — с якорем: `[R7](../../0-vibes/prd/PRD.md#r7)`. Путь за
ссылкой — навигация, и ведёт его скрипт, а не автор: переписывает при переносе
в `obsolete/` и при снимке PRD. Проверка падает, когда текст ссылки и её цель
называют разные id. Руками артефакты не переносить и не копировать. Голый id —
не ссылка: он отправляет читателя в поиск, а поиск находит и мёртвые копии.

Ссылки на всё остальное — `README.md`, папку `raw/<дата>/`, прогон, `docs/…` —
обычные: видимый текст — путь или название.

Имя файла начинается с id, поэтому id находится глобом по началу имени:
`**/ACTOR-1-*.md`, а у файлов без названия — `**/RESULT-TASK-3-01.md`.

## Один артефакт — один файл

Один актор — один файл, одно событие — один файл, одно требование — один
`R{n}`. Файл с двумя артефактами нельзя ни заморозить, ни процитировать, ни
похоронить по отдельности.

## Трассировка идёт вверх

Каждый артефакт ссылается на id, из которых выведен. Только вверх: артефакт не
перечисляет то, что позже выведено из него, иначе замороженный файл пришлось бы
править при каждом новом потомке. Единственная ссылка вперёд — «чем заменён» в
шапке похороненного артефакта.

## Код ссылается на артефакты

Спеки и дизайн не ссылаются на пути кода: код переезжает, а артефакт заморожен.
Связь идёт от кода: он несёт метку — голый id в комментарии или в имени теста.

- Код, который реализует UC, несёт `UC-{n}`.
- Тест несёт метку пути, который проверяет: в Dart — в имени,
  `test('UC-3-P-02: неверный пароль …')`; в SQL и Python — комментарием
  `-- UC-3-P-02` или `# UC-3-P-02` у проверки.
- Каждый файл темы `lib/app/theme/` несёт `TOKEN-{n}` группы, которую
  воплощает; виджет компонента — `COMP-{n}`.

Где реализован артефакт, показывает индекс, который скрипт строит по меткам.
Задания, сдачи и приёмки — записи своего момента, в них пути кода и хэши
коммитов уместны.

## Устаревание

Артефакт, который больше не верен, **хоронят** — не удаляют и не исправляют:

1. Переносят в `obsolete/` рядом с живыми — скриптом, который переписывает все
   ссылки на старое место.
2. Сверху файла пишут шапку: **когда**, **почему** и **чем заменён** — id или
   «ничем», если понятие снято.
3. Заменяющий артефакт пишет строку `supersedes: [<старый id>](путь)`.

Устаревшее не помечается на месте и не остаётся среди живых: в листинге живой
папки его нет. Исключение одно — требование `R{n}` в PRD (ниже).

## Устарелость выводится, а не записывается

Ссылка на похороненный id — устаревшая. Этого нигде не записывают: id
разрешают и смотрят, где он лежит. `obsolete/` — это и есть отметка; у
требования — отметка «устарело» в PRD.

Живой артефакт со ссылкой на похороненный id **отмечается к пересмотру, но не
хоронится сам**. Большинство изменений не убивает большинство зависимых. Какие
из них действительно умерли, решает человек. Так же и с кодом: старая метка
похороненного id — к пересмотру, а не ошибка.

Замороженное имя файла с похороненным id верно и остаётся: оно записывает, из
чего артефакт выведен. Это происхождение, а не живой указатель.

## Новое ссылается только на живые id

Прежде чем сослаться, id разрешают и проверяют, что он не похоронен. Это
касается и меток: новая метка в коде не ведёт на похороненный id.

## Id и ссылки ведёт скрипт конвейера

Id и ссылки ведёт один скрипт, а не руки: `python3 -m sdlc_tool`. Что он
делает, какие форматы читает и что именно проверяет — `sdlc_tool/README.md`.
Его пишет и меняет постановщик с одобрения владельца — это не задание
конвейера.

- Id выдаёт только `next`; номер на глаз не выбирают.
- Хоронит и снимает PRD только скрипт (`entomb`, `snapshot-prd`): он же
  переписывает пути в ссылках.
- Перед каждым коммитом, который меняет артефакты или код, — `views`, затем
  `check` без ошибок; та же проверка идёт в CI. `check` ловит нарушения этого
  закона: повторный или выданный не по порядку id, правку замороженного,
  ссылку, чей текст не id её цели, новую ссылку или метку на похороненное.
- Производные файлы — `INDEX.md` в папках с артефактами и
  `6-eval/DASHBOARD.md` — коммитят, но собирает их только скрипт:
  детерминированно, без даты сборки. Конфликт слияния в них руками не решают:
  берут любую сторону и пересобирают. Чего в коде ещё нет — метки, теста у пути
  UC, — то они показывают как «не покрыто»; ошибкой это не считается.
- Проверки проекта прогоняет `run` и записывает прогон в `6-eval/auto/`.

## Проход предлагает, человек одобряет

Новые данные меняют PRD, PRD меняет то, что верно ниже по течению. Агент
вычисляет разницу — что создать, что похоронить и какое изменение PRD за этим
стоит — и **показывает её на одобрение, прежде чем что-то сдвинется**.

Одобряется план, а не каждая запись: одно решение на проход, а не пятьдесят.

## PRD — изменяемый контейнер замороженных требований

`0-vibes/prd/PRD.md` — единственный PRD и единственный файл, который
переписывается на месте. Прежние версии скрипт снимает в `0-vibes/prd/history/`.

Требования внутри заморожены: текст `R7` не меняется. Требование, которое
больше не верно, отмечают устаревшим **на месте** — в формате
`0-vibes/prd/AGENTS.md`, чтобы отметку видел скрипт. Оно навсегда остаётся в
текущем PRD, а на замену выдаётся новый `R{n}`.

Поэтому `history/` нужна только для расследований. Каждая ссылка дерева
разрешается по текущему PRD, и чтобы ответить «что такое R7?», старая версия не
нужна.

## Находка — не задание

Найденное вне задания по ходу работы или приёмки записывают в сдачу или
приёмку — раздел «Найдено вне задания». Постановщик при приёмке переносит
находку заметкой в `0-vibes/raw/<дата>/`. Попутно её не чинят. Заданием
находка становится только через проход — PRD, бизнес-задача, спеки — и по
решению владельца. Следующее задание берут из бизнес-задач планирования, а не
из находок прошлой приёмки.

## Задания в работе не пересекаются

Задание пишут, когда его запускают; заранее задания не готовят. Очередь работы
— открытые бизнес-задачи `1-business-tasks/planning/`.

Заданий в работе может быть несколько, если они не пересекаются — не трогают
одни и те же файлы кода и таблицы. Пересечение постановщик проверяет перед
запуском; пересекающееся задание ждёт приёмки «принято» у того, с которым
пересекается.

Каждое задание выполняется в своём git worktree на ветке `task/TASK-{n}`.
Работа, сдачи и приёмки задания попадают в `main` только после «принято».
Боевую базу меняет одно задание за раз.

## Граница с контентом

Работа с контентом — банком ФИПИ и задачами проекта (`tasks/`): выгрузка,
конвертация, решение, заливка, публикация — идёт мимо конвейера. Её скрипты
лежат в `tools/` (см. `tools/README.md`). Стык с продуктом — Content API
(`docs/content-api.md`).

Изменение кода продукта (`lib/`, `test/`, `web/`, `supabase/`, CI), схемы, API
или клиента делается только заданием конвейера, даже если оно нужно контенту.
Мимо заданий идут только контентные скрипты `tools/` и скрипт конвейера с его
подключением к CI.
Найденное в контенте, что задевает учеников, — заметкой в
`0-vibes/raw/<дата>/`.

## Ответы и ключи — только указатели

В `sdlc/` не попадают ответы задач, эталонные решения, ключи, пароли и строки
подключения — ни в текст артефактов, ни в приведённые в них выводы команд.
Вместо них — указатели: путь (`supabase/seed/local/`), имя переменной
(`SEED_DATABASE_URL`), slug задачи.

## Правила — ровно в одном файле

Правила для агентов — в `AGENTS.md`: этот файл не привязан к инструменту, его
найдёт любой агент. `CLAUDE.md` в каждой папке — заглушка, которая импортирует
свой `AGENTS.md` и все родительские вплоть до этого, потому что Claude Code сам
`AGENTS.md` не читает.

Правило в `CLAUDE.md` не копируют, правило родителя в дочерней папке не
повторяют. Если правишь `CLAUDE.md` — правишь не тот файл.

## Два вида папок

- **Папки структуры** — нумерованные стадии и их подпапки. В каждой
  `README.md`, `AGENTS.md` и заглушка `CLAUDE.md`.
- **Папки содержимого** — `obsolete/`, `raw/<дата>/`, прогоны в
  `6-eval/auto/` и раунды в `6-eval/manual/`, папка разбитого файла. В них
  данные, а не правила, и файлов соглашений в них нет никогда.

Производные файлы (`INDEX.md`, `DASHBOARD.md`) — не правила и не артефакты: их
пишет только скрипт.

## Разбиение больших файлов

Растут только изменяемые файлы, на деле — один PRD. Больше ~300 строк — `check`
предупреждает, и PRD разбивают скриптом в папку с тем же именем без расширения:
`PRD.md` становится `PRD/` с `PRD.md`, `PRD-Requirements.md` и так далее.
Ссылки идут по id, пути переписывает скрипт, так что разбиение ничего не ломает.

`AGENTS.md` и `README.md` не разбиваются: это порвёт цепочку импортов. Если
такой файл подходит к 300 строкам, значит, правил слишком много или папка
делает слишком много. Его сокращают.

## Язык

Правила и артефакты пишутся по-русски. Имена в id — латиница в верхнем
регистре: `ACTOR-1-STUDENT-IN-AUTH`. Слово-тип id (`TASK`, `RESULT`, `TOKEN`
и другие из таблицы) в именах не используют: `ENT-3-TASK-…` читается как
ссылка на задание.

Термины, которые легко спутать:

- **задание** (TASK) — работа исполнителя;
- **бизнес-задача** (BT) — всегда полностью, не «задача»;
- **задача** — задача ученика в каталоге;
- **номер КЕГЭ** — номер задания экзамена: «номер 24», а не «задание 24».

## Стадии не пропускаются

Спека ссылается на бизнес-задачу, дизайн — на спеку, задание — на спеки и,
если задевает экраны, на дизайн. Перед записью в стадию прочитать её
`AGENTS.md`.
