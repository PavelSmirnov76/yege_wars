## Часть 1. Реализация

### Данные и состояние

Реализовать контракт ENT-18. В domain поместить чистые сущности сводки,
строки по номеру и краткой попытки, интерфейс репозитория и use-case чтения.
Data использует существующий SupabaseClient и отображение ошибок в Failure.
В presentation использовать сгенерированные Riverpod-провайдеры.

Суммировать агрегаты RPC, а последние попытки ограничивать на сервере.
Два запроса дают одно состояние загрузки. Ошибка любого запроса показывает
ошибку с повтором, повтор заново выполняет оба. При свежей загрузке предыдущие
числа не должны выглядеть актуальными данными нового аккаунта.

Учесть обычный вход в профиль, прямой адрес, возврат в уже созданную ветку
после отправки, повторное нажатие выбранного пункта профиля и смену аккаунта.
Поздний ответ старого запроса не меняет новое состояние. Подключить обновление
через текущую навигацию и состояние авторизации.

Запросы работают с текущей схемой. Если прямой запрос ENT-18 невозможно
выполнить через существующие права/связи, остановиться и показать конкретный
отказ. Контракт и схему самостоятельно не расширять.

### Экран

Заменить заглушку по FIG-23. Добавить компоненты COMP-17/COMP-18 и все
перечисленные ключи l10n. Строка попытки открывает штатный именованный маршрут
задачи с её slug, в том числе когда ветка каталога хранит другую задачу.
Вердикт обозначается текстом и цветом. Длинные названия переносятся,
дата показывается в локальном часовом поясе.

Сохранить показ логина/роли и выход по UC-4/UC-13. Код и виджеты несут
метки реализованных UC и компонентов, новые ссылки ведут на живые артефакты.

### Тесты и подготовка ручной проверки

Написать тесты путей из «Основания». Проверить значения сумм, повторную верную
попытку, исключение скрытых задач и возврат после публикации на уровне
запроса/существующего RPC, группу без номера, пустую базу и нулевой прогресс.
Тесты клиента проверяют, что серверному запросу переданы user_id, статус,
оба порядка и limit 10, даже когда RLS допускает чужие опубликованные попытки.

Проверить ошибку каждого запроса, повтор, предел десять, стабильный порядок
при равном времени, возврат после отправки и переход к точному slug.
Отдельно проверить смену аккаунта при ещё выполняющемся запросе и обычный
переход между ветками реального роутера. Имитирующие данные тесты относятся
к проверке клиента. Реальное чтение dev сверяется отдельно по TC-19.

Для TC-19 подготовить воспроизводимый Playwright-драйвер с сетевыми подменами
Supabase только нужных запросов. Фикстуры и команды передать в сдаче,
без необходимости править исходники перед каждым состоянием. Драйвер
делегируется Luna. При проверке возврата после отправки submit подменяется
до ухода запроса в сеть, данные попыток меняются в том же fixture-состоянии.
Подход и изолированный Chromium — по `docs/BROWSER_CHECKS.md`.
Драйвер/фикстуры допустимы в `test/`, команды и версии — в сдаче.
Их независимый прогон выполняет тестировщик постановщика по готовому кейсу.

```bash

$FL pub get

$FL test
find lib test -name '*.dart' -not -name '*.g.dart' -not -path 'lib/l10n/gen/*' -print0 | xargs -0 $DA format --output=none --set-exit-if-changed
```

`bash supabase/tests/run_local.sh` до `RLS OK` для независимого подтверждения
контракта прогресса и доступа, используемого новым клиентом.
При изменении только упавшего теста повторяются относящиеся к правке
проверки. Повтор успешной проверки требует конкретной причины.
