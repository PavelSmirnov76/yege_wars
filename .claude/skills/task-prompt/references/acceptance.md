# Приёмка сдачи

Цель — проверить результат своими руками, а не по словам исполнителя. Итог
исполнителя в чате и его сдача — только список того, что нужно проверить.

## 1. Что сделано и как

- `git log --oneline main..task/TASK-{n}`, `git -C ../yege_wars-TASK-{n}
  status`, `git show --stat <коммит>`: коммиты в ветке задания, лишнего в них
  нет (`reference/`, секреты, `*.g.dart`), `main` исполнитель не трогал. Хэш в
  разделе «Коммит работы» сдачи совпадает с `git log`. Сдача закоммичена
  отдельно от работы.
- Прочитать сдачу целиком и сверить её состав с `sdlc/5-results/AGENTS.md`.
- **Транскрипт сессии исполнителя** —
  `~/.claude/projects/-Users-pavelsmirnov-projects-yege-wars/<id>.jsonl`.
  Нужная сессия — свежая, первое сообщение в ней «выполни
  sdlc/4-tasks/TASK-…» (после возврата — с припиской «возврат по ACC-…»). Из
  транскрипта проверить:
  - **обсуждение**: ответы владельца лежат в `toolUseResult.answers` у вызовов
    AskUserQuestion. Сверить с разделом «Обсуждение» сдачи: все ли вопросы
    записаны и верно ли; при СТОПе 0 — ответ получен по каждому пункту плана;
  - **стопы**: остановился ли исполнитель там, где велело задание, и ждал ли
    «да»;
  - **обращения к боевой и внешним сервисам**: Bash-вызовы с
    `SEED_DATABASE_URL`, `psql`, `curl`. На боевой — только миграции задания,
    данные через Content API не трогали; применённое совпадает с разделом
    «Применено к боевой»;
  - **субагенты** — транскрипты в `<id>/subagents/*.jsonl`, их проверить тем же
    способом;
  - **`sdlc/`**: исполнитель не менял ничего, кроме своей сдачи и производных
    файлов.

## 2. Независимая перепроверка каждого пункта «Приёмки»

- **Проверки проекта** запустить заново в worktree задания:
  `python3 -m sdlc_tool run` — он запишет прогон в `sdlc/6-eval/auto/`. Идёт
  минутами — в фоне.
- **«Тест не холостой»** — на копии каталога во временной папке, без новой
  миграции. Рабочее дерево не трогать.
- **Метки**: тесты путей из «Основания» задания помечены этими путями, скрипт
  конвейера их видит.
- **Боевая — только чтение.** Состояние сверить своим запросом или скриптом с
  первоисточником, печатая числа, а не секреты. Где возможно, сравнить с
  дампом «до» (блоки `COPY`), а не с контрольными суммами из сдачи.
- **Утверждения о поведении кода** проверить по коду.
- **Утечки**: ответы и эталоны не встречаются ни в сдаче, ни в
  `git show <коммит>`.
- **Своё** (скрипты, логи) — в scratchpad сессии, не в репозиторий и не в
  выгрузку.

## 3. Итог

Записать приёмку `sdlc/6-eval/acceptance/ACC-TASK-{n}-{NN}.md` по составу из
`AGENTS.md` той папки — в worktree задания; имя —
`python3 -m sdlc_tool next ACC RESULT-TASK-{n}-{NN}`. Найденное вне задания —
ещё и заметкой в `sdlc/0-vibes/raw/<дата>/`, там же.

Владельцу — коротко: принято или возврат, что проверено, находки. Затем один
вопрос с вариантами: одобрить ли итог. Решение владельца — в приёмку, затем
`python3 -m sdlc_tool views`, `python3 -m sdlc_tool check` и коммит приёмки в
ветку задания.

**Принято** — влить ветку в основной копии и убрать worktree:

```bash
git merge --no-ff task/TASK-{n}       # конфликт в INDEX.md и DASHBOARD.md — взять любую сторону
python3 -m sdlc_tool views && python3 -m sdlc_tool check
git commit                            # если views что-то изменил или был конфликт
git worktree remove ../yege_wars-TASK-{n}
git branch -d task/TASK-{n}
```

**Возврат** — worktree и ветка остаются, исполнителя запускают фразой «выполни
sdlc/4-tasks/TASK-{n}-{TITLE}.md, возврат по ACC-TASK-{n}-{NN}».

Следующий шаг предлагается из открытых бизнес-задач планирования, а не из
находок (закон, «Находка — не задание»).
