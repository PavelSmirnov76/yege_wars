# Задание исполнителю и приёмка

Роли — постановщик, исполнитель, владелец — по закону конвейера
(`sdlc/AGENTS.md`, «Роли»). Исполнителя запускают фразой «выполни
sdlc/4-tasks/TASK-{n}-{TITLE}.md», и о проекте он знает только то, что есть в
репозитории. Поэтому задание самодостаточно.

Итог работы не теряется в чате: исполнитель пишет сдачу, постановщик —
приёмку. Что в них, задают `sdlc/5-results/AGENTS.md` и
`sdlc/6-eval/acceptance/AGENTS.md`; задание — `sdlc/4-tasks/AGENTS.md`. Здесь —
как их делать.

## Порядок постановки

### 0. Что ставить

Следующее задание берут из открытых бизнес-задач планирования
(`sdlc/1-business-tasks/planning/INDEX.md`), а не из находок прошлой приёмки
(закон, «Находка — не задание»). Постановщик предлагает шаг, владелец выбирает.

Задания в работе не пересекаются (закон, «Задания в работе не пересекаются»).
Задания в работе — ветки `task/TASK-…` в `git worktree list`. Сверить с ними
«Основание» нового задания и файлы и таблицы, которые оно затронет. Пересекается
— новое ждёт «принято» того задания.

### 1. Собрать факты, а не вспоминать

Прочитать основание задания — пути UC, экраны, компоненты, токены,
бизнес-задачу, — затем прошлые сдачи и приёмки по теме и код, который задание
затронет. Каждое утверждение, которое попадёт в «Исходное
состояние», проверить командой сейчас и указать дату проверки: состояние git,
базовый прогон проверок, факты о боевой базе (только чтение).

**Как работает код, проверять по коду.** Утверждение из сдачи или журнала
исполнителя — ещё не факт. Однажды постановщик передал пользователю «кнопка
соберёт табличный ответ», не открыв клиент, а кнопка брала только последнюю
строку. На этом утверждении строилось решение о публикации.

Боевая база — только чтение: `set default_transaction_read_only = on` или
`begin read only`. Доступы — `set -a; . supabase/.env.local; set +a`.
Значения переменных никуда не выводить.

### 2. Развилки — владельцу, до написания

Всё, что меняет содержание задания (объём, механизм, трогать ли боевую),
спросить через AskUserQuestion. Вопросы короткие, у каждого варианта — факты и
следствия, рекомендуемый вариант первым. Пользователь просил «полноценные
вопросы без стены текста». Мелкие технические решения внутри выбранного объёма
постановщик принимает сам. И ответы владельца, и свои решения записывают в
раздел задания «Решения, принятые при постановке» — с пометкой, чьё решение.

### 3. Написать задание по шаблону

Шаблон и обязательные блоки — в `references/template.md`. Прочитать его перед
написанием. Id задания выдаёт скрипт конвейера.

Что делает задание хорошим:

- **Исходное состояние — таблица фактов с датой.** Пути, имена функций, числа,
  известные ловушки (например: «`admin_upsert_task` стирает вложения из
  Storage»).
- **Контракт — из спеки.** RPC, коды ошибок, права и состав экрана задание
  берёт из спек и дизайна по ссылкам «Основания», а не придумывает. Чего в
  спеке нет — сначала проход, потом задание.
- **СТОП 0 — план решений до кода**, когда устройство под контракт выбирает
  исполнитель. Блок шаблона переносится как есть.
- **Стопы стоят перед каждым необратимым шагом**: применением к боевой и
  коммитом. Стоп-условия названы явно, и при них исполнитель не чинит сам, а
  докладывает.
- **На боевой задание меняет только схему — миграциями**: дамп → снимок «до» →
  миграция → проверка на одном объекте → снимок «после». Данные
  через Content API (публикация, заливка) — работа с контентом, её в задание не
  включают (закон, «Граница с контентом»).
- **Тесты метятся путями UC**: задание называет пути, тесты которых пишет
  исполнитель.
- **Приёмка проверяется независимо.** Каждый пункт постановщик сможет
  проверить сам, своими командами.
- **Ожидаемые значения в «Приёмке» проверены на текущих данных**, как и факты
  исходного состояния. Однажды промт ждал «каталог начинается с номера 1», а
  опубликованных задач этого номера не было.
- **Секреты** — по закону («Ответы и ключи — только указатели»): вывод команд
  попадает в транскрипт, поэтому ответов и эталонов нет и в нём.
- **Качество из `CLAUDE.md`**: для Dart — полный набор проверок, для БД —
  `run_local.sh` до `RLS OK`, для Python — unittest, Python 3.9.

Язык — русский. Пишется для агента без контекста чата: коротко, однозначно,
без оценок объёма и времени.

### 4. Одобрение и запуск

- Задание — владельцу. До коммита его правят свободно: замораживает коммит.
- После «да» — пересборка производных файлов, проверка скриптом, коммит
  задания в `main` («Задание TASK-{n}: <что>»).
- Worktree задания рядом с репозиторием и ссылка на доступы к боевой:
  ```bash
  git worktree add ../yege_wars-TASK-{n} -b task/TASK-{n} main
  ln -s ~/projects/yege_wars/supabase/.env.local ../yege_wars-TASK-{n}/supabase/.env.local
  ```
- Владельцу — одна строка, для кого написано задание, затем коротко, что в
  нём важно, и фраза запуска новой сессии из корня репозитория: «выполни
  sdlc/4-tasks/TASK-{n}-{TITLE}.md». В worktree исполнитель переходит сам, по
  разделу задания «Где работать».

## Приёмка

Когда исполнитель сдал («проверь», вставленный итог исполнителя), прочитать
`references/acceptance.md` и пройти его. Коротко: сдача и транскрипт сессии,
независимая перепроверка каждого пункта «Приёмки», приёмка отдельным файлом,
итог владельцу, коммит после его «да»; при «принято» — вливание ветки в
`main`, при возврате — повторный запуск исполнителя.

## Чего не делать

- Не просить в сдаче «мысли» или «размышления» агента. Такая просьба уже ломала
  сессию: фильтр принимал её за выгрузку внутренних рассуждений модели. Нужны
  факты, решения и вопросы с ответами владельца.
- Не предлагать находку следующим заданием в обход прохода и не готовить
  задания впрок.
- Не выдавать своё соглашение за правило пользователя и не записывать его в
  `CLAUDE.md` или в закон конвейера от его имени.
- Не коммитить без подтверждения владельца.
