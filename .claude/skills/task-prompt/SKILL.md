# Промт для исполнителя и приёмка

В проекте две роли. **Постановщик** пишет задание и принимает результат.
**Исполнитель** — отдельная сессия: её запускают фразой «выполни
docs/PROMPT_<ИМЯ>.md», и о проекте она знает только то, что есть в
репозитории и в `CLAUDE.md`. Поэтому промт самодостаточен: всё, что
исполнитель должен знать, написано в нём или в файлах, на которые он
ссылается.

Итог работы не должен теряться в чате. Исполнитель ведёт отчёт-файл, а
в отчёте есть журнал решений, найденное по ходу и коммит. Постановщик
дописывает в тот же файл раздел «Приёмка».

## Порядок составления

### 1. Собрать факты, а не вспоминать

Прочитать `docs/STATE.md` (особенно «Чего ещё нет»), отчёты прошлых
заданий (`docs/*_REPORT.md`) и код, который задача затронет. Каждое
утверждение, которое попадёт в «Исходное состояние», проверить командой
сейчас и указать дату проверки: состояние git, базовый прогон проверок,
факты о боевой базе (только чтение).

**Как работает код, проверять по коду.** Утверждение из отчёта или
журнала исполнителя — ещё не факт. Однажды постановщик передал
пользователю «кнопка соберёт табличный ответ», не открыв клиент, а кнопка
брала только последнюю строку. На этом утверждении строилось решение
о публикации.

Боевая база — только чтение: `set default_transaction_read_only = on`
или `begin read only`. Доступы — `set -a; . supabase/.env.local; set +a`.
Значения переменных никуда не выводить.

### 2. Развилки — пользователю, до написания

Всё, что меняет содержание задания (объём, механизм, трогать ли боевую,
что публиковать), спросить через AskUserQuestion. Вопросы короткие,
у каждого варианта — факты и следствия, рекомендуемый вариант первым.
Пользователь просил «полноценные вопросы без стены текста». Мелкие
технические решения внутри выбранного объёма постановщик принимает сам
и записывает в промт.

### 3. Написать промт по шаблону

Шаблон и обязательные блоки — в `references/template.md`. Прочитать его
перед написанием. Файл — `docs/PROMPT_<ИМЯ>.md`, отчёт исполнителя —
`docs/<ИМЯ>_REPORT.md`.

Что делает промт хорошим:

- **Ответы пользователя записаны в шапке**, в «Решения, принятые при
  постановке». Так они попадут в отчёт, и исполнитель не будет
  переспрашивать.
- **Исходное состояние — таблица фактов с датой.** Пути, имена функций,
  числа, известные ловушки (например: «`admin_upsert_task` стирает
  вложения из Storage»).
- **Стопы стоят перед каждым необратимым шагом**: применением к боевой и
  коммитом. Стоп-условия названы явно, и при них исполнитель не чинит
  сам, а докладывает.
- **Работа на боевой** идёт так: дамп → снимок «до» → изменение →
  пилот на одном объекте → всё остальное → снимок «после». Только через
  миграции и Content API. Выводы «до» и «после» — в отчёт дословно.
- **Приёмка проверяется независимо.** Каждый пункт постановщик сможет
  проверить сам, своими командами.
- **Ожидаемые значения в «Приёмке» проверены на текущих данных**, как и
  факты исходного состояния. Однажды промт ждал «каталог начинается
  с номера 1», а опубликованных задач этого номера не было.
- **Секреты.** Ответы задач и эталоны лежат только локально: не в git,
  не в отчёте, не в выводе команд (вывод попадает в транскрипт).
- **Качество из `CLAUDE.md`**: для Dart — полный набор проверок, для БД —
  `run_local.sh` до `RLS OK`, для Python — unittest, Python 3.9.

Язык — русский. Пишется для агента без контекста чата: коротко,
однозначно, без оценок объёма и времени.

### 4. Подготовить запуск

- В `CLAUDE.md` указатель «текущее задание» переключить на новый промт.
  В «Исходном состоянии» промта записать, что `CLAUDE.md` и сам промт
  не закоммичены и идут в коммит исполнителя как есть.
- Обновить память проекта: какое задание следующее и какие решения
  принял пользователь.
- Пользователю — одна строка, для кого написан промт, затем коротко, что
  в нём важно, и фраза запуска: «выполни docs/PROMPT_<ИМЯ>.md».

## Приёмка

Когда исполнитель закончил («проверь», вставленный итог исполнителя),
прочитать `references/acceptance.md` и пройти его. Коротко: отчёт и
транскрипт сессии, независимая перепроверка каждого пункта «Приёмки»,
раздел «Приёмка» в конец отчёта, коммит после подтверждения, следующий
шаг — вопросом.

## Чего не делать

- Не просить в отчёте «мысли» или «размышления» агента. Такая просьба уже
  ломала сессию: фильтр принимал её за выгрузку внутренних рассуждений
  модели. Нужны факты, решения и вопросы с ответами пользователя.
- Не выдавать своё соглашение за правило пользователя и не записывать
  его в `CLAUDE.md` от его имени.
- Не коммитить без подтверждения пользователя.
